# 肉身碎裂暫停／奪舍恢復：機制與解析檔案

更新：2026-10-02。以下以用戶最後確認的規則為準。

## 1. 生效範圍

**碎裂後，只暫停該 Telegram 帳號發送以 `.` 開頭的遊戲指令。**

- 包括 `.探寻裂缝`、`.血洗山林`、`.深度闭关` 等，以及重試提交。
- 忽略開頭空白；兼容現有指令解析使用的全形 `。`。
- 文字訊息、媒體說明及編輯成點指令，都會檢查；批量媒體有點指令時不提交該批次。
- **不攔截 MiniApp、青元子 HTTP 操作、普通聊天、Telegram 按鈕或 WebView 操作。**
- 不影響其他帳號，不清除原有伺服器冷卻、不補發過期事件。
- 不自動發送奪舍指令、不自動選擇肉身。用戶在 Telegram App 的手動操作不經過本地腳本攔截。

最初版本把全部 Telegram 寫入及 MiniApp 都攔截，已依用戶修正要求撤回，不能沿用舊版範圍。

## 2. 怎樣偵測碎裂

來源：主指令群 `-1009400000004` 的話題 `7310786`。

必須同時滿足：

1. 回覆發送者在已核實的官方遊戲機器人 ID 白名單。
2. 回覆直接指向一條本方帳號發出的點指令。
3. 原指令屬於正確群組、話題；以原指令的 Telegram sender ID 定位帳號，不用旁觀帳號或任意文字提及代替。
4. 回覆符合已知格式之一：
   - `【元婴遁逃·虚弱】`，同時有 `6小时`、`无法进行夺舍`；
   - 全文為單層 `*...*` 的碎裂狀態說話，不是普通內容中出現一個星號或 Markdown 粗體標題；
   - `.夺舍重生` 收到 `无法承受夺舍`、`请再温养 ...` 的官方虛弱回覆。

原始碎裂回覆提供六小時起點；只有星號回覆時，先暫停但不猜起點。後續重複星號回覆不會重設六小時。官方剩餘溫養時間可更新到期估算。

## 3. 後續怎樣偵測奪舍成功

常駐 `account-lifecycle.monitor` 監聽 Telegram **NewMessage 與 MessageEdited**，並每 60 秒做一次歷史補查。讀取範圍：

- 主指令群：`-1009400000004`；
- 遊戲公告群：`-1009400000005`，**只讀，不會向該群發送指令**。

### 路徑 A：主群直接回覆

官方回覆必須精確關聯該帳號在主話題發出的 `.夺舍重生` 或 `.重生 1/2/3`，正文為已核實的完整成功回覆：

```text
夺舍成功！你的神魂与新肉身完美融合，所有被封存的神通宝物已尽数回归！
```

不以單獨的「成功」子字串判斷；`夺舍失败`、`尚未夺舍成功`、選肉身選單、尋找肉身中的回覆均不恢復。

### 路徑 B：另一個遊戲群的公開成功公告

本次找到的真實格式：

```text
【天机异闻·夺舍重生】
先前肉身陨落的 @demo_player_02 (原道号：示例修士二)，其元婴已成功夺舍重生！
从今日起，他将以【示例重生角色】为名，身负【伪灵根(金水土木)】的全新肉身，继续其漫漫仙途！过往因果，一并继承！
```

這類公告**沒有 reply_to**，不能硬要求它回覆主群指令。現在有獨立解析器：

- 必須來自兩個已知讀取群之一及可信官方 bot；
- 對整段公告做結構化全文匹配，核對標題、成功句、新道號／肉身及結尾；
- 只提取「先前肉身陨落的 @username」這個主語，與帳號表精確比對；
- `@demo_player_02_fake`、第三者附帶提及 `@demo_player_02`、轉述／失敗句均不當作本方成功；
- 公告時間必須新於該帳號需要處理的狀態；跨群補查按官方時間合併，不把不同群的 message ID 當成同一條時間軸。

### 恢復動作

辨認成功後，原子更新該帳號 `paused → active`，保存證據及重播保護時間，排入一次性恢復通知。

排程及監聽器本身不需要關掉：每次發點指令前讀取狀態，恢復後按各腳本正常節奏與原有冷卻继续執行。**不是把全部腳本強行立即發一輪，也不清空每個流程的合法冷卻。**

六小時到期只提醒，不憑時間直接解鎖。普通指令偶爾成功亦不是奪舍成功證據。

用戶明確確認成功並要求恢復時，可以作人工確認，必須記錄 `operator_confirmed_possession`，不能冒充官方回執。稍後找到官方證據時再附入紀錄。

## 5. 解析參考與本地實作

### 本地生效代碼

- `account_lifecycle.py`
  - `classify_reply`：主群回覆、碎裂、溫養及直接成功。
  - `classify_recovery_announcement`：跨群公開成功公告，精確主語帳號匹配。

## 6. 狀態、運維與驗證

- 狀態：`state/account_lifecycle.json`；由 `account_lifecycle.py` 的加鎖 transaction 原子更新。
- 單例監聽：`ai.hermes.xiuxian.account-lifecycle.monitor`。
- 通知：既有 Hermes 主人通知渠道，outbox 去重；一般在下一次 60 秒處理循環送出，限流或通知服務故障會延後。
- 暫停狀態跨程序／重啟持續有效。已提交到網路的請求無法撤回。
- 兩群各補查最近 300 條；啟動另查每類最多 50 條相關回執，不是無限歷史審計。
- 不支援自動讀取任意私訊／未知群；新 bot ID、新成功格式須先核實再加解析，不會自行猜測恢復。
- 純 Telegram 點指令策略部署記錄：`state/account_lifecycle/dot_only_reload.json`。
