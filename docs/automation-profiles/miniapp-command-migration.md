## 运行与恢复

实现集中在 `miniapp_commands/`。原 sender 标签、原账号锁和原日程继续工作；
`transport: miniapp` 是显式切换标记。宗门日常 helper 单独声明 `miniapp_commands: [".宗门点卯"]`。
只读归来监听继续存在，其后续调用会进入新 API 路径。无新增本机任务，也无第二个常驻业务写入器。

每个流程继续由原 sender 持有 `state/accounts/<账号>/<流程>/send.lock`；
点卯位于 `sect_daily` 目录。新的状态和证据为 `miniapp_state.json`、`miniapp_last_result.json`，
保留旧 Telegram 回执供追溯，绝不制造消息 ID 或把 API 回执伪装成群回复。
共享 `state/miniapp_commands/api.lock` 串行化新增 API 会话；青元子优先窗口和账号暂停门继续有效。

每次写操作先记待确认日志，再请求服务器。闭关和元婴从实际状态、实际剩余时间恢复；不强行出关、不提前召回。
点卯按服务器每日幂等规则恢复。问道、血洗和召唤结果不明时保留完整冷却，防止短时间重复消耗。
同一布道事件结果不明时保留待确认问题，不在下一轮冷却结束后重复布道。
429 / 官方限流按 5、15、60 分钟退避。MiniApp 失败后只等待或报错，不退回群发送。

既有 30 秒 deadline dispatcher 读取新状态的 `next_due_ts`；不再用旧群 pending 和旧倒计时唤醒迁移流程。
健康检查区分服务器计时、成功、失败结算和结果不明；一次正常进程退出不等于游戏收益成功。
确认获得的稀有物品继续进入既有通知收件箱。自动任务档案采集新回执的白名单字段，认证值和完整响应不入档。
