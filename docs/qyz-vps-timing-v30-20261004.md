# 青元子 v30：VPS 延迟参数与反馈修正

用户要求修改不适合当前环境的参数，并 commit、push。本轮已将10月4日复盘中的反馈问题
落实到 `qyz_timing.VpsTimingMixin`，正式 `ProtocolRuntime` 使用该适配层。

## 改动

| 项目 | 原逻辑 | v30 |
| --- | --- | --- |
| 反馈目标 | 把本次有符号误差当作下一次绝对提前量 | 使用扣除基础提前量后的残余延迟 |
| 长尾门槛 | 固定500ms后降权，仍进入历史 | 超过 `max(250ms, 2.5 × 本场基础RTT)` 的样本不进入漂移估计 |
| 历史长度 | 5个混合方向样本 | 3个；方向反转后清空旧方向历史 |
| 增益 | 0.30 | 0.45 × 方向置信度；单次最多调整80ms |
| 方向 | 旧历史可能推动反向更新 | 偏早不会继续增加提前量，偏晚不会降低提前量；扣除有意蓄力救援偏移 |
| 本地迟发 | 可能当成网络漂移 | 超过20ms时跳过样本，避免把等待charge回包当成持续网络偏差 |
| 蓄力学习 | 两个请求低于固定400ms即可学习 | 增加随基础RTT变化的门槛；显著不对称请求不再污染后续蓄力估计 |
| 蓄力夹紧 | 先夹紧1000ms基准，再加150ms | 先算 `1150ms − 已学习偏差`，再在560–1210ms夹紧 |

例如001第8窗明确偏早210.2ms，旧提前量仍从217.304增至244.663ms。
新规则在这个决策点降低提前量，受每次80ms限制。本场13个反向更新样本都有对应测试。

三个参考源文件及其受保护函数体不变，原哈希校验通过。实际HTTP请求数量、票据要求、
按真实经过时间上报的hold/elapsed、正式结算流程保持有效；没有伪造服务器证据。

## 基础蓄力目标保留1150ms的依据

固定原请求延迟的单变量敏感度检查显示，直接改成1000ms会从68降为65个PERFECT，
1050ms为67；1100ms为69，但正常命中的蓄力收益也会下降，不能由此证明总伤害提高。
该检查不是重赛，不用于宣称真实成绩提升。

因此没有一律缩短蓄力。本轮实际修改了反馈目标、RTT门槛、历史长度、增益、步长上限、
本地迟发过滤、非对称请求过滤和夹紧顺序。慢charge仍可能造成服务端票据年龄不足。
